### The result that matters

Three of the seven screens — Unlock, Next Steps, Plan — depend on the unlock graph (M2) and
the derived plan (M3), which don't exist. As of today they have a **contract fixed and
pinned by tests**, with the data that already exists in front (catalog, save, goals) and a
**typed, declared placeholder** (`{ kind: "stub" }`) where the graph is needed. When M2 and
M3 arrive, three fields will change value (`graph`, `basis`, `expansion`), no type and no
component. The webapp can proceed.

On the real profile the junction between achievement and slot in section 1 is **`slot[id]`**: of
the 171 items seen in section 4 that declare `unlocked_by`, 169 have the achievement done
(the alternatives `slot[id − 1]` and `slot[id + 1]` give 145 and 142; the two disagreements
are items that can be seen without having their unlock). Slots 638–641 lie beyond the
catalog's last achievement: four `unknown` nodes, three of which are done, i.e. "known index,
unknown name" with a real number.

And **`store` was born**: a SQLite file with a versioned schema and a single table, `goals`.
Plan goals are the first data the app writes, and it writes only there: saves stay read-only
by construction, `store` doesn't even know about `core-save`.

## Decisions made during execution

- **`store_available` is derived, not declared.** The spec said "a `StoreUnavailable`
  diagnostic"; the plan had reduced it to a boolean because that's what the frontend consumes
  as a gate. The Task 7 review showed that the boolean alone loses the reason (a newer schema
  is the one case the user can act on, and it needs to be stated). The final shape has both,
  from **a single source**: `plan_view(goals, unreadable, store_unavailable:
  Option<String>)` produces `store_available = is_none()` and the
  `StoreUnavailable { reason }` diagnostic. A test pins that they can't disagree.
- **The store's state keeps the `String` of the reason, not an `IpcError`.** With
  `Result<Mutex<Store>, IpcError>`, `plan` would have needed a seven-arm `match` with six
  impossible cases (a `NoActiveProfile` inside the store's state makes no sense, but the type
  would allow it). With the string those cases don't exist by construction: the state carries
  exactly what it knows, and the two consumers each wrap it in their own type
  (`PlanDiagnostic::StoreUnavailable` for `plan`, `IpcError::StoreUnavailable` for the write
  commands). The text belongs to the app, never to SQLite: "unreadable database", "database
  from a newer version (N > M)".
- **`IpcError::CatalogUnavailable` distinguished from `UnknownTarget`.** "The catalog doesn't
  know this target" and "I can't verify it" are different errors for the user. Today the
  second one only fires when the game is missing: `ResourceSet::open` and `Catalog::build`
  never fail, an unreadable `packed` folder gives an empty catalog and therefore
  `UnknownTarget`. The comment on the variant says so.
- **`target_exists` lives in `ipc`, not in `app`.** It's verifiable logic (a target on a
  made-up id doesn't save): per the rule "if it has a return value worth checking, it belongs
  in a pure crate" it sits next to `kind_view`, with its inverse `item_kind` and a real test
  covering the four item types.
- **`app/src/store.rs` became `settings_file.rs`.** The local module (I/O for
  `settings.json`) collided with the `store` crate; the new name says what it does, an alias
  for the crate would have hidden the collision.
- **The store's poisoned mutex is recovered** with `into_inner`: `Store` has no invariants a
  panic could break, so a poisoned guard isn't a reason to deny service for the process's
  whole lifetime.
- **`kind_view` unified.** The plan proposed a local copy in `graph.rs`; execution pulled out
  the one already inline in `catalog_view::item_views` and reused it. A single implementation
  of the `ItemKind → ItemKindView` map.
- **`itemKind` is the existing tagged enum** — *reversed by the final review.* The plan
  assumed `itemKind: "passive"`; in the code `ItemKindView` was already `{ kind: "passive" }`,
  and that single truth was kept. Finding 6 then established the opposite, general rule (a
  fieldless enum is a plain string), so `itemKind` went back to `"passive"` — i.e. to what
  the plan said. The lesson isn't "the plan was right": it's that consistency needed to be
  sought among the IPC's unit enums, not between `ItemView.kind` and itself.
- **`Unlock` derives `Ord`** for the reverse index's deterministic ordering instead of a
  hand-written comparator: the order of the variants in the declaration is the one pinned by
  the test.
- **`GoalId::new` with no UUID crate**: 128 bits from time, an allocation's address, and the
  pid. Enough to distinguish goals on the same machine; it's not a security token, and the
  doc says so.
- **The double `ResourceSet::open` is left at the already-open block.** `unlock` and
  `add_goal` each open their own archive set (1.3 GB per call) and `next_steps` goes through
  `unlock`. It's the same defect as `Archive::open` loading everything into memory, logged in
  `docs/STATUS.md` before this plan: it gets fixed there, in `unpack`, not with a cache in the
  commands.
- **No worktree for this plan**, as with previous ones: the real tests depend on the
  git-ignored `samples/packed` junction and on the `live.*` profile.

## Deviations from the spec, declared

- **Goals aren't saved as `UnlockTarget`.** The spec said "the `UnlockTarget`'s JSON in
  `target_json`". The on-disk format is `TargetKey` (identity only) and the view-model is
  rebuilt on every read with `resolve_target`: see finding 1 of the final review.
  The type `PlanView` exposes is `GoalView`, not `Goal`; `Goal` stays internal between `ipc`
  and `store` and doesn't cross the IPC.
- `PlanView` carries `diagnostics: Vec<PlanDiagnostic>` **and** `store_available: bool`,
  derived from the same source (see above); the spec only called for the diagnostic. Added
  the variants `UnreadableGoal { id }`, `NoCatalog`, and `UnresolvedGoal { id }`, which the
  spec didn't have.
- `plan_view(catalog: Option<&Catalog>, goals: Vec<Goal>, unreadable: Vec<GoalId>,
  store_unavailable: Option<String>, icon: impl FnMut(&str) -> Option<Vec<u8>>)` instead of
  `plan_view(goals: &[Goal], store_ok: bool)`: the catalog enters the plan because it's the
  one that gives goals their name and icon.
- `unlock_view` takes `flags: Option<&[bool]>`, not `&[bool]`: an unreadable section 1 is a
  case to declare (`NoAchievementSection`), not an empty save.
- `UnlockDiagnostic` has a fourth variant beyond the spec, `NoAchievementSection`.
- `Store::goals() -> Result<GoalsRead, StoreError>` instead of `Result<Vec<Goal>>`;
  `StoreError` has two variants (`Unreadable`, `NewerSchema`), the intermediate `Corrupt` was
  removed. The `goals` table has a fifth column, `seq`, that preserves insertion order.
  `add_goal` just inserts: an id that already exists is an error, not an update.
- `IpcError::CatalogUnavailable`, not called for by the spec.
- The slots unknown to the catalog on the real profile are **4**, not 5 (spec corrected in
  `c1d492e`).
- The spec's unit test "goals from `Settings`" doesn't exist: goals were never sourced from
  `settings.json`, the non-regression test on `Settings` had nothing to protect.
- The criterion "a goal added survives an app restart" is verified by `store`'s test
  (reopening without rerunning the migration), not by hand in the app: the verification
  screen still has no UI for the Plan, as planned.

## The lesson in method

For the third time in a row a number written in a plan was wrong, and for the third time the
rule "the number isn't fixed, it's investigated" held: Task 6's execution stopped with a red
test and measured against the flags before touching the fixture. This time the cause wasn't a
text `grep` but a counting ambiguity — `642 − 637` includes slot 0, which the contract doesn't
treat as a node. The shape of the error is the same: a subtraction done in one's head on two
correct numbers gives a wrong number if the two bases don't count the same things. From this
the rule extends to arithmetic too: an expected number in a fixture is measured against the
crate's code (a probe that prints `nodes.len()`, `known`, `unknown`), and the comment in the
test says **what** each term counts.
